# Releases

Releases are created automatically from Conventional Commits. Only the deploy-relevant prefixes create a release and a Docker image:

```text
feat:
fix:
perf:
security:
```

Hidden maintenance commits such as `docs:`, `test:`, `ci:`, or `chore:` do not create a release or Docker image.

Release images are pushed to GHCR:

```text
ghcr.io/eric-schubert/shiftplan:latest
ghcr.io/eric-schubert/shiftplan:<version>
```

`<version>` has no `v` prefix: the Git tag `v3.10.3` becomes the image tag `3.10.3`. Each image is also tagged with its short commit SHA.

### Workflow Summary

| Workflow | Runs On | Main Result |
|----------|---------|-------------|
| CI | Push and PR: master | Docs check on every PR; for code changes tests, file length, typecheck (app and server), and Docker build with smoke test |
| Auto Version & Release | CI success on push: master | Creates version tag and GitHub release for changelog-visible commits, one at a time |
| Docker Build & Push | CI success + deploy prefix: master | Builds and pushes GHCR image with generated changelog; only the newest release moves `latest` |

### Changelog Prefixes

Release and deploy prefix rules are defined in `scripts/release-prefixes.json`.

Visible in releases: `feat:`, `fix:`, `perf:`, `security:`

Hidden from releases: `refactor:`, `style:`, `test:`, `chore:`, `ci:`, `docs:`, `build:`, `revert:`

### Deploy Flow

1. CI validates tests, typecheck, and the Docker image build.
2. After CI passed on master, Auto Version & Release creates a tag for visible commit prefixes. A commit that a newer tag already contains gets none.
3. Docker waits for the release tag, generates the in-app changelog, and pushes the image.
4. Hidden prefixes such as docs, chore, ci, and test do not create releases or Docker images.
5. CI fails when the generated docs are stale, also for docs-only changes; run `npm run docs` and commit the result.
